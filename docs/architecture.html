架构总览

kg-acme

一个知识图谱能力中枢：通过单一 CLI 发现、校验并路由所有 KG 操作，同时把全部算法逻辑保留在独立的 provider 二进制中。

产品介绍

kg-acme 是一个遵循 acme 家族模式的能力中枢：hub 负责集成（发现、协议、catalog、策略、路由），而每个 KG 算法都独立成单独的 provider 二进制。hub 从不臆造 provider 选项 —— 能力的 flags、枚举、输入模式完全来自 provider 自身的 describe --json 自描述。

三个入口共享同一份不可变的能力快照：

  • kg —— 执行面。接受无前缀的点号式语义 ID（如 kg analyze.pagerank）。
  • kgctl —— 控制面。负责刷新、provider 诊断、能力搜索、路由配置与 shell 补全。
  • kg-mcp —— 一个 stdio MCP 服务。把每个可用能力都以 JSON-RPC 工具的形式，通过换行分隔的 stdin/stdout 发布出去。

特性

发现 Provider 自动发现

扫描 ~/sync 下的二进制与 PATH，识别协议原生与遗留的 provider 二进制。通过 describe --json 与 available --json 探测每一个。

协议 Provider 自描述

Provider 通过 kg.provider/v1 声明能力、输入模式、CLI 规约与副作用。hub 协商版本，并按内嵌的 JSON Schema 校验清单。

策略 副作用门

所有副作用门（网络、数据外发、模型下载、写库）默认关闭。必须用 --allow-* 显式开启。--dry-run 产出零副作用的执行计划。

流水线 声明式 DAG 执行

多阶段流水线（kg.pipeline/v1），具备类型化产物边、拓扑排序、产物校验和与基于工作目录的断点续跑。

MCP AI Agent 集成

kg-mcp 把每个能力都以 JSON-RPC 工具的形式暴露在 stdio 上，提供 dry_run 与 allow_* 参数。兼容 Claude Code、Codex 等 MCP host。

快照 不可变能力目录

kgctl refresh 生成带指纹的快照。所有 help、list、describe、补全与 MCP 操作只读这份快照 —— 不会启动 provider 进程。

架构走读

1

Provider 发现 (discover)

运行 kgctl refresh 时，hub 在四个位置扫描 provider 二进制：显式的 --provider-bin 覆盖、~/sync/<os>-<arch>-bin/、~/sync/bin/ 与 PATH。此外，还会扫描 PATH 中所有 kg-provider-* 可执行文件。每个二进制都会通过 describe --json 和 available --json 进行探测（每次探测 15 秒超时）。

2

协议协商 (protocol)

清单的 protocol_versions 与 hub 的 SupportedVersions 取交集（[1]）。最高的共有版本胜出。版本不匹配只会产生 VersionError 诊断，不会硬失败 —— 该 provider 仍可通过兜底 bridge 使用。

3

Schema 校验 (schema)

Provider 清单按内嵌的 provider-v1.schema.json 进行校验。来自 acme-core 的描述质量门槛会拒掉那些描述信息量过低的清单。输入对象在执行前会按各能力声明的 input_schema 进行校验。

4

Surface 构建 (surface)

快照把所有 provider 能力合并成扁平化的公共清单。每个能力获得一个带 kg. 前缀的语义 ID（如 kg.extract.entities-relations）。候选者按以下规则排序：已探测 provider 优先于兜底 bridge；并列时按权重（降序），再按 provider ID。快照以 SHA-256 指纹并原子写入。

5

路由与解析 (router)

在调用时，快照中的候选列表选出一个 provider。hub 先针对快照校验输入（无需启动 provider 进程）。然后才 重新探测 选中的 provider，以捕获快照创建和调用之间的契约漂移。

6

策略执行 (policy)

四个副作用门（network、data_egress、downloads_models、writes_db）默认全部关闭。每个能力声明其副作用；hub 在执行前检查所有副作用都已被显式允许。未知副作用一律 fail-closed。--dry-run 绕过所有门，仅渲染执行计划。

7

Provider 派发 (router.Execute)

已探测的 provider 通过 kg.execution/v1 调用：hub 把 JSON 请求写到 stdin 并从 stdout 读取一个 Envelope。遗留 provider 通过 bridge 调用：hub 从 cli_spec 渲染 argv 数组，并把 stdout 包装为 Envelope。两条路径产出相同的输出契约。

8

流水线执行 (pipeline)

流水线用类型化产物边声明阶段。运行器通过 Kahn 算法编译 DAG，校验边的类型（只有 artifact 模式输出可向下游传递），前置检查所有副作用门的并集，然后按拓扑序执行阶段。每个阶段的 envelope 写入 <work-dir>/stage-<id>.envelope.json，以支持基于校验和验证的产物复用续跑。

9

MCP 集成 (kg-mcp)

MCP 服务在启动时读取快照，把每个可用能力暴露为名为 kg_<capability> 的 JSON-RPC 工具（点和短横线被替换成下划线）。工具调用被派发到 cli.Runner 并带上相应 flags，包括注入到每个工具输入模式中的 dry_run 与 allow_* 参数。

关键设计决策

Hub 永不实现算法

所有 KG 计算都放在 provider 二进制中。hub 只做集成：发现、协议、catalog、策略、路由与流水线编排。这让 hub 保持小巧，也让算法面可以独立测试。

Provider 自描述是权威

当 provider 的 describe --json 与 hub 兜底 bridge 表冲突时，以 provider 为准。会发射一条诊断，但 hub 端没有任何硬编码会覆盖 provider 契约。

快照隔离

元数据操作（help、list、describe、补全、MCP tools/list）永不启动 provider 进程。它们只读取 kgctl refresh 时生成的不可变快照。

Fail-Closed 策略

所有副作用门默认拒绝。未知副作用一律拒绝。流水线预检查会在任何 provider 启动前计算所有阶段副作用的并集。这能避免意外的网络外发或写库。
