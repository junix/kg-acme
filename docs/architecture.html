Architecture Overview

kg-acme

A knowledge-graph capability hub that discovers, validates, and routes every KG operation through a single CLI, while keeping all algorithm logic inside independent provider binaries.

Product Introduction

kg-acme is a capability hub following the acme family pattern: the hub owns integration (discovery, protocol, catalog, policy, routing) while every KG algorithm lives in a separate provider binary. The hub never invents provider options — everything about a capability's flags, enums, and input schema comes from the provider's own describe --json self-description.

Three entry points share one immutable capability snapshot:

  • kg — the execution surface. Accepts prefix-free dotted Semantic IDs (e.g. kg analyze.pagerank).
  • kgctl — the control plane. Manages refresh, provider diagnostics, capability search, route configuration, and shell completion.
  • kg-mcp — a stdio MCP server. Publishes every available capability as a JSON-RPC tool over newline-delimited stdin/stdout.

Features

Discovery Provider Auto-Discovery

Scans ~/sync bins and PATH for protocol-native and legacy provider binaries. Probes each via describe --json and available --json.

Protocol Self-Describing Providers

Providers declare capabilities, input schemas, CLI specs, and side effects through kg.provider/v1. The hub negotiates versions and validates manifests against embedded JSON Schemas.

Policy Side-Effect Gates

All gates (network, data egress, model download, DB write) are closed by default. Each must be opened explicitly with --allow-* flags. --dry-run plans with zero side effects.

Pipeline Declarative DAG Execution

Multi-stage pipelines (kg.pipeline/v1) with typed artifact edges, topological ordering, checksum-verified artifacts, and work-dir-based resume.

MCP AI-Agent Integration

kg-mcp serves every capability as a JSON-RPC tool over stdio, exposing dry_run and allow_* parameters. Compatible with Claude Code, Codex, and other MCP hosts.

Snapshot Immutable Capability Catalog

kgctl refresh generates a fingerprinted snapshot. All help, list, describe, completion, and MCP operations read only this snapshot — no provider processes start.

System Context

The kg-acme hub sits between operators (human or AI agent) and a fleet of independent KG provider binaries. It enforces a strict boundary: the hub handles protocol negotiation, catalog routing, schema validation, and policy enforcement. All computation (entity extraction, community detection, graph storage, etc.) happens inside provider processes.

Architecture Walkthrough

1

Provider Discovery (discover)

On kgctl refresh, the hub scans for provider binaries in four locations: explicit --provider-bin overrides, ~/sync/<os>-<arch>-bin/, ~/sync/bin/, and PATH. Additionally, it scans PATH for any kg-provider-* executables. Each binary is probed with describe --json and available --json (15-second timeout per probe).

2

Protocol Negotiation (protocol)

The manifest's protocol_versions are intersected with the hub's SupportedVersions ([1]). The highest common version wins. A version mismatch produces a VersionError diagnostic, not a hard failure — the provider remains usable via the fallback bridge.

3

Schema Validation (schema)

Provider manifests are validated against the embedded provider-v1.schema.json. A description-quality floor (from acme-core) rejects manifests with low-information descriptions. Input objects are validated against each capability's declared input_schema before execution.

4

Surface Building (surface)

The snapshot merges all provider capabilities into a flat public inventory. Each capability gets a kg.-prefixed Semantic ID (e.g. kg.extract.entities-relations). Candidates are ranked: probed providers beat fallback bridges; ties break on weight (desc), then provider ID. The snapshot is fingerprinted with SHA-256 and written atomically.

5

Routing & Resolution (router)

At invocation time, the snapshot's candidate list selects a provider. The hub first validates input against the snapshot (no provider process needed). Only then does it re-probe the selected provider to catch contract drift between snapshot creation and invocation.

6

Policy Enforcement (policy)

Four side-effect gates (network, data_egress, downloads_models, writes_db) are all closed by default. Each capability declares its side effects; the hub checks all are explicitly allowed before execution. Unknown side effects fail closed. --dry-run bypasses all gates and renders the execution plan instead.

7

Provider Dispatch (router.Execute)

Probed providers are invoked via kg.execution/v1: the hub writes a JSON request to stdin and reads one Envelope from stdout. Legacy providers are invoked through the bridge: the hub renders an argv vector from the cli_spec and wraps stdout into an Envelope. Both paths produce the same output contract.

8

Pipeline Execution (pipeline)

Pipelines declare stages with typed artifact edges. The runner compiles the DAG via Kahn's algorithm, validates edge types (only artifact-mode outputs can feed downstream), checks the union of all side-effect gates upfront, then executes stages in topological order. Each stage's envelope is written to <work-dir>/stage-<id>.envelope.json, enabling resume with checksum-verified artifact reuse.

9

MCP Integration (kg-mcp)

The MCP server reads the snapshot at startup and exposes each available capability as a JSON-RPC tool named kg_<capability> (dots and dashes replaced with underscores). Tool calls are dispatched to cli.Runner with the appropriate flags, including dry_run and allow_* parameters injected into every tool's input schema.

Key Design Decisions

Hub Never Implements Algorithms

All KG computation lives in provider binaries. The hub only does integration: discovery, protocol, catalog, policy, routing, and pipeline orchestration. This keeps the hub small and the algorithm surface independently testable.

Provider Self-Description Is Authoritative

When a provider's describe --json conflicts with the hub's fallback bridge table, the provider wins. A diagnostic is emitted, but no hub-side hardcoding overrides the provider contract.

Snapshot Isolation

Metadata operations (help, list, describe, completion, MCP tools/list) never start provider processes. They read only the immutable snapshot generated at kgctl refresh time.

Fail-Closed Policy

All side-effect gates default to denied. Unknown side effects are denied. Pipeline pre-check computes the union of all stage side effects before any provider starts. This prevents accidental network egress or database writes.
